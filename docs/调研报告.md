# 调研报告：把 DSH 搬到手机上的另一种做法

> 目标：**手机只负责连接**，所有能力留在电脑上；配对只用「B2 的 4 项 + 1 个密码」，
> 每次数据都是**标准 7z 加密包**。
>
> 本文记录为什么这么设计、协议长什么样、踩了哪些坑、成本多少、边界在哪。

---

## 1. 起点：参考实现是怎么做的

隔壁 `dsh手机` 工作区里的桌面插件（`dsh-jiuling-remote-desktop`）走的是这条路：

```
APK ──► 配对服务器（发激活码 / 建隧道 / 建 DNS）
     ──► Cloudflare 隧道 ──► 电脑上的本地中继 127.0.0.1:17890
```

中继本身很干净，值得原样保留：

| 端点 | 用途 |
| --- | --- |
| `POST /api/dsh-remote-control/rpc` | 一次性调用（`ping` / `listWorkspaces` / `readHistory` / `prompt` / `cancel` / `pendingAsks` / `answerAsk` / `createSession` …） |
| `GET /api/dsh-remote-control/stream?session=<id>&fromSeq=<n>` | SSE：`event: event`（durable）、`frame:`（流式）、`ask`（审批） |
| 鉴权头 | `x-dsh-remote-control-token` |

它的**公网那一截**有三个必须解决的成本：要有一个公网可达的入口（隧道或端口映射）、
要有一个帮你发配对码的服务器、APK 里要塞下「懂 DSH 事件」的渲染逻辑（那份客户端
有上万行）。

本项目的取舍：**中继一行不改，只把「公网那一截」换成一个对象存储邮箱**，
并把渲染搬到电脑侧。

### 1.1 候选通路对比

| 方案 | 手机侧配置 | 电脑侧要求 | 加密 | 代价 |
| --- | --- | --- | --- | --- |
| Cloudflare 隧道（参考实现） | 配对码 | 装 cloudflared、有配对服务器 | TLS（可选端到端） | 依赖第三方服务与域名 |
| 自建 frp / WireGuard + VPS | 服务器地址 + 密钥 | 有公网 IP 或 VPS | 取决于配置 | 要买 VPS、要维护 |
| 局域网直连 | 内网 IP | 同一 WiFi | TLS | 出门就废 |
| WebDAV（坚果云等） | 账号密码 | 无 | 靠服务端 | 语义是「文件」，没有列举游标的低成本原语 |
| **对象存储邮箱（本项目）** | **4 项 + 1 密码** | **无（只要能出网）** | **每对象 7z AES-256** | **轮询成本**（见 §6） |

选对象存储的理由很直接：**它天生就有「按名字排序 + 从游标之后列举」这个原语**
（`b2_list_file_names` 的 `startFileName`），而这正是「收件箱」需要的东西；
而且不需要电脑有公网 IP、不需要额外的服务器。选 **B2 Native API** 而不是 S3 兼容
API 的原因：限定到单桶的 Application Key 在 `b2_authorize_account` 里就直接返回
`apiUrl` / `downloadUrl` / `bucketId`，不用自己配 endpoint 与 SigV4 签名。

## 2. 协议：两条队列，各一个生产者

```
手机                                                  电脑
put  from-phone/0001794483231981.7z    ────────────►    pull from-phone/
pull from-desktop/0001794483231985.7z ◄────────────    put  from-desktop/
```

目录名由**生产者**命名（谁写的），不靠视角区分。早期版本用的是 `in/` `out/`，
那是站电脑角度取的（in = 进电脑），两端共用同一套逻辑时极容易把方向读反；
而且 `in` `out` 太通用，翻桶时看不出是哪个软件。v2 改成 `from-phone` /
`from-desktop` 后，方向在名字里，不依赖任何上下文。

四条规则撑起整个协议：

1. **一步只有一个生产者**：手机只写 `from-phone/`，电脑只写 `from-desktop/`。
2. **序号由生产者本地单调递增**，对象名 `from-phone/<13 位十进制>.7z`；消费者用
   `startFileName` 从游标之后开始列 ⇒ 每次轮询**恒定 1 次列举**，不随积压变贵。
3. **首次运行的序号起点是 `Date.now()`**（13 位毫秒），不是 1。这样即使手机端
   应用数据被清、序号「从头开始」，也仍然**大于**上一轮的最大值 —— 消费方游标
   不会因为序号变小而永久卡住。
4. **一个对象里装多帧**：打包 7z 有固定开销（见 §4.4），逐帧打包不划算。
   失败重试的粒度是一批，而每帧自带 `id`，应用层幂等（`prompt` 带 `requestId`）。

于是**不需要分布式锁、不需要 CAS、不需要处理版本冲突** —— B2 那个「最后写入者胜」
的对象模型就够了。

### 2.1 帧类型

| kind | 方向 | 说明 |
| --- | --- | --- |
| `hb` | 双向 | 心跳（手机 30s、电脑 30s）。只用来点亮「在线」，不产生回包 |
| `ctl` | 手机→电脑 | `{type:'sub'|'unsub', sessionId, fromSeq}`：让电脑替你订阅 SSE |
| `req` | 手机→电脑 | `{id, method, params}`：`app/*` 或任意中继方法名 |
| `res` | 电脑→手机 | `{id, ok, result|error}` |
| `ev` | 电脑→手机 | `{sessionId, items:[...]}`：**已渲染好的气泡**（见 §3） |
| `ask` | 电脑→手机 | `{requestId, askKind, sessionId, payload}`：审批弹窗 |

### 2.2 坏帧与游标

密码填错、对象损坏时，解不开的**对象不删除**：

- 那是唯一的线索，删了就永久没了（可以在桶里人工取回）；
- 但**游标照样前移**，否则一条坏帧会把整条队列堵死。

这条规则两端都实现了（`mailbox.js` 与 `Mailbox.java`），并且有专门的测试项：
「错误密码的对象不会堵死队列」。

### 2.3 在线判定

| 侧 | 心跳间隔 | 「对方在线」窗口 |
| --- | --- | --- |
| 电脑 | 30s（且要求手机在 5 分钟内有过动静） | — |
| 手机 | 30s | 90s 内收到过电脑的帧 |

心跳只在**有人用**的时候发（电脑侧要求 `lastAppSeenAt` 在 5 分钟内），
所以手机放着不管时，电脑会安静下来，不白白消耗额度。

## 3. 渲染放在电脑端

DSH 的事件形状（取自本机真实会话日志，不是猜的）：

```
user/message      {seq,time,data:{content:[{type:'text',text}],source:{kind:'user'}}}
assistant/message {seq,time,data:{turn,step,message:{content:[{type:'text'}|{type:'tool-call',name}]}}}
assistant/chunk   {seq,time,data:{chunk:{type:'block-start',blockType}}}
text-chunks       {seq0,time0,data:{turn,step,index,dt:[...],texts:[...]}}   ← 没有 seq
tool/call         {seq,time,data:{turn,step,callId,name,arguments}}
tool/result       {seq,time,data:{message:{content:[{type:'tool-result',...}]}}}
turn/start|end    {seq,time,data:{turn}}
```

如果手机自己读这些，它就得懂 `assistant/chunk` / `text-chunks` / `surfaceOp` /
`sourceEventSeqs` 一整套语义 —— 那正是参考实现里那上万行客户端的来源。

本方案让桥**代替手机订阅** SSE，并用 `render.js` 把事件折成四种条目：

| 条目 | 手机上做什么 |
| --- | --- |
| `{op:'add', role, text, seq, tools}` | 追加一个气泡 |
| `{op:'live', text}` | 拼到「正在说」的那个气泡尾部（虚线 + 光标） |
| `{op:'live-reset'}` | 当前流式块收了，清掉临时气泡 |
| `{op:'busy', busy}` | 转圈 |
| `{op:'tool', name}` | 一行灰字「用了什么工具」 |

三个好处：APK 里没有 DSH 知识（升级 DSH 不用重装 APK）、事件只折一次（不占手机 CPU）、
协议面小到可以人工核对。

**攒批**是必须的：逐字流式一秒几十帧，一帧一个 B2 对象既慢又贵。桥按
「400ms 或 8KB」两个阈值刷一次，手机上看到的是**一段一段**冒字。

> 一个细节：`text-chunks` 只有 `seq0`（本批第一块的序号），拿它推进游标会把游标
> 钉在错误位置。所以规矩是：**游标只由带 `seq` 的 durable 事件推进**，
> `text-chunks` 只贡献显示用的增量文本。

## 4. 7z 封装：为什么、怎么做、坑在哪

### 4.1 为什么是「标准 7z」而不是自研格式

要求是「每次数据都用 7z 标准压缩加密上传」。除了字面满足，它带来三个实际好处：

1. **可验证**：任何一台装了 7-Zip 的机器都能 `7z t` / `7z e -so` 人工核对，
   不需要我们的代码；
2. **两端可以各写各的**：Node 侧调系统的 `7z.exe`（成熟、快），Java 侧自己实现
   （APK 里不能依赖外部程序）—— 然后用真实的 `7z.exe` 做**双向互验**；
3. **失败模式明确**：密码错、包坏、头加密，都有清晰的报错，而不是「解析异常」。

### 4.2 容器结构（实测，不是猜的）

```
37 7A BC AF 27 1C            magic
00 04                        版本
<4B>                         StartHeaderCRC（覆盖后面 20 字节）
<8B>                         NextHeaderOffset = 前面压缩数据的长度
<8B>                         NextHeaderSize
<4B>                         NextHeaderCRC
<压缩数据>                     ← 只有一个 pack stream（一个文件、一条流）
<头>
```

头（`kHeader = 0x01`）里的关键顺序：

```
01 04                                  Header / MainStreamsInfo
  06  PackPos=0  NumPackStreams=1  09 <packSize>  00
  07  0B  NumFolders=1  external=0  NumCoders=2
        24 06F10701 <18B props>        ← 7zAES：AES-256 + SHA-256
        23 030101   <5B props>         ← LZMA
        <bind pair: AES 的输入来自 LZMA 的输出>
      0C <lzmaSize> <原文长度>          ← 每个 out stream 一个
      00
05  01  NumFiles=1  11 <名字长度> 00 <UTF-16LE 名字> 00 00  00 00  00
```

### 4.3 7zAES 的关键配方

**KDF**（唯一正确的那一种，链式哈希的三种变体全都解不出来）：

```
h = SHA-256()
重复 (1 << cycles) 次:
    h.update(salt)
    h.update(password 的 UTF-16LE 字节)
    h.update(计数器 round 的小端 8 字节)
key = h.digest() 的前 32 字节
```

- 加密：AES-256-**CBC**，IV 16 字节，**无填充语义**（按 unpackSize 截断）
- 属性：`first = cycles | (salt>=16 ? 0x80 : 0) | (iv>=16 ? 0x40 : 0)`，
  `second = ((salt>=16 ? 15 : salt) << 4) | (iv>=16 ? 15 : iv)`
  ⇒ iv=16 时属性正好是 `53 0F` + 16 字节 IV = 18 字节

这套配方与 py7zr 的 `calculate_key()` 一致，用 `{"x":2}` 这种最小载荷逐字节对齐过。

### 4.4 踩过的坑（每一条都真实卡了很久）

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| `7z t` 报 `Cannot open the file as [7z] archive` | `NextHeaderOffset` 写成 0 | 写成**压缩数据的长度** |
| `Open ERROR: Unsupported Method : m.json` | 7zAES 属性第二字节的 nibble 编码错 | 按 `size = flag + nibble` 重算 |
| `Unsupported ... 0xf10701` | 读 coder 方法 ID 时 `& 0xFFFFFF` 把 4 字节截断了 | 直接按 4 字节存 |
| 写 2 个 `CodersUnPackSize` 报 Unsupported、写 1 个报 Headers Error | 数量必须是**每个 out stream 一个** | 写两份（AES 输出 = LZMA 长度、LZMA 输出 = 原文长度） |
| 多写一个空的 `kSubStreamsInfo(0x08 0x00)` 就 Headers Error | 单文件单流时 `7z.exe` **不写**它 | 去掉，直接 `0x00` 结束 StreamsInfo |
| KDF 三种链式变体都解不出 | 正确的形式是**单个哈希上下文累加** | 见 §4.3 |

### 4.5 互验结果（真 `7z.exe`，双向）

```
① Java 打包 → 7z.exe：Everything is Ok，解出 {"hello":"世界","n":42}
② 7z.exe 普通归档 → Java：解出 hello
③ 7z.exe -mhe=on（加密头）→ Java：解出 hello
④ Node packJson（邮件帧）→ Java：解出 {"v":1,"frames":[...]}
```

`-mhe=on`（加密文件名与头）**读**是支持的（头本身是 `0x17 kEncodedHeader`，先解头再解数据）；
写的时候刻意用 `-mhe=off`：头里只有 `m.json` 一个名字，加密它换不来实质收益，
却让两端的写实现都复杂一截。

### 4.6 性能（实测）

| 操作 | 耗时 | 备注 |
| --- | --- | --- |
| Node 侧一次打包（spawn `7z.exe`） | ~60–90ms | 进程启动占大头 |
| Node 侧一次解包 | ~60ms | 同上 |
| **Java 侧打包 + 解包（进程内）** | **往返 39ms** | 没有进程启动开销，明显更快 |
| 设置页「测试往返」端到端 | 156ms | 含一次上传 + 一次列举 + 一次下载 + 一次删除 |
| 一个 138B 的 JSON | 7z 包 266B | 压缩比没意义，要的是加密 |

这解释了为什么「一对象多帧」是必须的：如果 500ms 内来了 20 条流式帧，
逐帧打包就是 20 × 87ms，链路直接堵死。

## 5. 通道派生与配对

```
salt      = "dsh-remote-control/v2|<bucket>|<cloudFile>"
channelId = HMAC-SHA256(appKey, "channel-id|" + salt) 的十六进制前 12 位
root      = "dsh-remote-control/v2/<cloudFile>/ch/<channelId>"
fingerprint = SHA-256(salt + "|" + channelId) 的前 8 位十六进制
```

- 两端拿同样五项的**前四项**就能算出同一个 `channelId`，不需要任何服务器牵线；
- `fingerprint` 只用来**对人**：两端显示同一个 8 位串，人对一眼就知道配对没错；
- **密码故意不参与派生**。密码填错时应该得到「7z 解不开」的明确错误，
  而不是悄悄换到另一条空通道上、让人以为是网络问题。

`cloudFile` 会被清洗（`[^\w.-]` → `_`，最长 120 字符），所以「云端文件名」里
写中文、空格、斜杠都不会破坏对象名。

### 5.0.1 `cloudFile` 就是「哪台电脑」

派生式子里只有 `appKey + bucket + cloudFile` 三个输入，所以：

| 变化 | 结果 |
| --- | --- |
| 只有 `cloudFile` 不同 | **通道 ID 与前缀都不同 ⇒ 一条全新通道**，两台机器各收各的 |
| `cloudFile` 相同、`appKey` 不同 | 通道也不同（`appKey` 是 HMAC 密钥），但通常拿不到同一个桶的另一种 key |
| `appKeyId` 不同 | **不影响通道**（它只在 HTTP Basic 认证里出现，不参与派生） |
| `password` 不同 | **不影响通道**，但两端密码不一致就解不开 |

由此得出两个产品结论：

1. 加一台电脑**只需要改这一项**，其余四项照抄；
2. 这一项重复 ⇒ 两台机器抢同一条队列。所以手机端新增电脑时会用**机器名自动
   派生**一个默认值（`desk-win`、`desktop-8k3f2l`），并保证在已有档案里不重复
   （撞了追加 `-2`）。

派生规则两端必须逐字一致（`Config.defaultCloudFile` / `defaultCloudFile`）：

```
转小写 → 非 [a-z0-9] 折成 "-" → 去首尾/重复 "-" → 截 40
全被折光时（中文名）→ "desk-" + sha256(原串) 前 6 位
```

**为什么不保留中文**：两端的清洗分别跑在 Java 与 JS 上，Unicode 归一化、大小写
折叠、`\w` 的差异任何一处不一致，同一台机器就会算出两条通道 —— 现象只是
「消息一直不来」，几乎无法归因。宁可退化成一个明显的自动生成名，让人一眼
认出这是默认值、再自己改。两个测试套件里各硬编码了同一组期望值
（`desk-ec4d11` / `desk-e3b0c4` / `desktop-8k3f2l`），任一端改规则就会红。

### 5.1 一台手机管多台电脑

协议层本来就不设上限：每台电脑在自己的 `$DSH_HOME/dsh-remote-control/config.json` 里
各有一份 5 项，通道 ID 由这份配置决定。所以「多电脑」不是协议问题，是手机端
**只存了一条配置**的问题。

改造点只有一个，但位置很关键：**所有状态都过 `Config.Store` 这一个接口**
（5 项配置、`cursor`、`outSeq`）。于是隔离做成一层 `ScopedStore` 前缀就够：

```
p.<id>.appKeyId … p.<id>.password … p.<id>.cursor … p.<id>.outSeq
```

`Config` 与 `RemoteLink` 一行都不用改，也就不存在「配置隔离了、游标忘了隔离」
这种半吊子状态 —— 那才是多设备最容易出的 bug：切过去之后静默漏消息，现象是
「消息莫名其妙少了几条」，几乎没法归因。

为什么不让两台电脑共用一组 5 项：一条通道只有一对队列，两个桥同时
轮询同一个 `from-phone/` 就是**抢消息**——谁先取走算谁的。所以每台的配置里必须有东西不同，
最自然的是 `cloudFile`（当机器名用）。

## 6. 成本与配额（这个方案的真正代价）

B2 的 Class C（列举）免费额度是 **2500 次/天**，超出按 $0.004 / 万次计。

本方案的轮询就是列举，两侧各自独立：

| 状态 | 轮询间隔 | 手机侧列举/天 | 总列举/天 | 超出后的钱 |
| --- | --- | --- | --- | --- |
| 活跃（有人在看） | 500ms | 172,800 | 345,600 | ≈ $0.14/天 |
| 刚离开 | 1.5s | 57,600 | 115,200 | ≈ $0.046/天 |
| 久无活动 | 4s | 21,600 | 43,200 | ≈ $0.017/天 |

**结论**：免费额度只够「4 秒轮询 1 小时」。要长期挂着，必须在
*Caps & Alerts* 里把 Transaction Cap 提上去（例如 50 万/天），
或者接受「按需点开才连」。

这也是为什么**测试默认打本地桩**（`tools/local-b2.mjs`）：项目开发期间
跑了几十轮端到端，真桶的额度很快就用完了 —— 这也是我们第一次看到
`transaction_cap_exceeded` 的来源。

> 想进一步省钱，有两条明确的路（本项目未实现，留给后续）：
> ① 把两条队列合成一条前缀、一次列举同时收两个方向（列举次数直接减半）；
> ② 手机侧在应用进后台时把间隔拉到 15–30s（代价是推送延迟变大）。

## 7. 安全边界

威胁模型：**桶对你是可写的、对公司运维是可读的、公网任何人可以尝试猜对象名。**

| 威胁 | 现状 |
| --- | --- |
| B2 / 中间人看到内容 | 看不到：每个对象都是 7z AES-256 密文，密码只在两端 |
| 别人拿到 bucket 读权限 | 看不到内容，但能看到**对象名**（次数、时间、大小）→ 元数据泄露 |
| 别人拿到 Application Key | 能删你的对象、能塞垃圾、能读到密文 ⇒ 应当**限桶 + 可随时吊销** |
| 密码太弱 | 离线暴力：7zAES 有迭代（`1<<cycles`，默认 19 ≈ 52 万次 SHA-256），但弱密码仍然可破。**请用 12 位以上随机串** |
| 重放 | 未做防重放。帧里有 `id`/`requestId`，`prompt` 是幂等的；但一个老对象被重新塞回 `from-phone/` 理论上会被当作新请求处理。**只对拿到写权限的人生效** |
| 通道 ID 碰撞 | 12 位十六进制 = 48 bit；由 `appKey`（服务端生成的强随机）参与派生，实际不会撞。即使撞了，密码不同 → 解不开 |
| 手机丢失 | 手机里存着 5 项（含密码）。APK 没做额外加密（依赖系统锁屏）；丢了应该**吊销 key + 换密码** |

明确**没有**做的事：消息签名/防重放、对象名混淆（可以哈希化以隐藏元数据）、
前向保密（换个密码不会让历史消息失效 —— 这是 7z 的固有性质）。

### 8.1 另一个真机坑：`confirm()` 是哑的

`MainActivity` 只挂了 `addJavascriptInterface`，没有 `WebChromeClient`。而 WebView
在缺少它的时候会**直接取消** JS 的 `confirm()` / `prompt()` —— `confirm` 恒返回 `false`。

后果：「清空通道」原来写的是 `if (!confirm(...)) return;`，在真机上等于**永远不会执行**，
而且不报错、不提示，看起来就像按钮坏了。这一版把它和「删除电脑」一起改成
**自绘弹层 + 连点两次确认**，UI 冒烟测试里也加了一条断言：脚本代码（去掉注释后）
不允许出现 `confirm(` / `prompt(`。

## 9. 已知限制

1. **延迟下限 1~2 秒**：一次列举 + 一次 7z 打包。流式文字按 400ms 批次到达，
   不是逐字。
2. **配额敏感**：见 §6，这是选这条路线的固有成本。
3. **渲染只做了文本**：图片、附件、终端彩色输出都没有；工具调用只显示名字，
   不显示参数与结果。
4. **没有多设备**：一条通道按「一台手机 + 一台电脑」设计。两个手机填同样的配置会
   争抢 `from-desktop/`（后启动的会把前一个的帧读走）。
5. **APK 未做发布级加固**：自签 debug 证书、没有混淆、没有 certificate pinning。
6. **`7z` 是外部依赖**（电脑侧）：没装 7-Zip 时设置页会明确报「7z 缺失」，
   但链路不可用。Java 侧不依赖它（自带实现），所以手机永远不需要 7z。

## 10. 如果要继续做

按性价比排序：

1. **合并两条队列**（列举次数减半，直接省钱）；
2. **对象名哈希化**（隐藏元数据：次数、时间、大小）；
3. **推进 `-mhe=on`**（读已经支持，写要补一段，让头里的文件名也加密）；
4. **手机侧后台降频**（进后台拉到 15–30s）；
5. **渲染补图片/附件**（电脑侧把附件先塞进同一个 7z 包，手机落地到应用私有目录）。
